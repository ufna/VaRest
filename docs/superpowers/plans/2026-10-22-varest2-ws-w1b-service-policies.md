## The seam with W1a

W1a leaves, ready for W1b:

- **The request** `FVaRestSocketConnectRequest` (`VaRestSocketTransport.h`): W1b adds `PingInterval`, `PingTimeout`, `MaxPendingInboundBytes`, `AutoReplies`. Each is a plain field with a default, so W1a's callers compile unchanged.
- **The deadlines loop**: `FConn::CheckDeadlines(FService&, double Now)`, `NextDeadline()`, `WantsShortWait()` (`VaRestLwsConn.cpp`) already handle the connect and close deadlines. `FService::ComputeWaitMs` takes the earliest `NextDeadline` of all connections. W1b adds the ping, ping-timeout and idle deadlines to the same three functions.
- **Kills** report at the decision (W1a decision 3) through `FConn::Kill` and `EndOpen`/`EndPreOpen`. The 100 ms wait cap while a kill is in flight (decision 12) bounds a heartbeat kill too. `EVaRestSocketFailure::HeartbeatTimeout`/`IdleTimeout` and `EVaRestSocketCloseBy::Heartbeat` exist (W1a decision 20).
- **The write path**: `FConn::OnWriteable` writes one frame per `WRITEABLE` [tx.two_writes_one_writeable]. `NextFragment == 0` marks a message boundary and `HeldBytes > 0` a write LWS still holds. A control frame may go between fragments [tx.ping_between_fragments]. A data reply goes only at a boundary (SW-5 b).
- **The receive path**: `FConn::OnReceive` (`VaRestLwsConnReceive.cpp`) pushes whole messages. `FSocketLink::PendingInboundBytes` counts the bytes pushed and not yet acknowledged through `IVaRestSocketConnection::Consumed(int64)`. `FEvents::bAcknowledge = false` lets a test hold them.
- **Events**: `EVaRestSocketEventType::Pong` with `FVaRestSocketEvent::Seconds` exists, but nothing produces it yet. `FVaRestFakeSocketAttempt::Pong` scripts one.
- **The proxy**: `FService::Start` already passes `FPlatformHttp::GetConfiguredProxyAddress()` as `http_proxy_address` (`LwsWebSocketsManager.cpp:196-203`). Task 5's table already maps the proxy's own error strings ("ERROR proxy: …", "proxy write failed") to `ConnectFailed`. No test exercises any of this yet.
- **The startup policy** (decision 8) runs in shared-copy builds only. W1a never ran such a build, beyond linking it (Task 14 Step 7).

## Design questions the W1b plan must settle (with the writer's recommendation)

1. **Can a proxied connection open at all with W1a's redirect veto? Answer this first.** W1a refuses an attempt at its second `APPEND_HANDSHAKE_HEADER` (decision 10). If LWS 3.0 calls `APPEND_HANDSHAKE_HEADER` both for the proxy's `CONNECT` exchange and for the upgrade, W1a refuses every proxied connection. The same holds if a wss attempt through a proxy makes its certificate check after the first `APPEND` (the `AppendCalls > 0` rule in `OnVerifyServerCertificate`). Recommendation: B1 measures both, through a CONNECT proxy in the test server, before any other W1b code. If either count differs, the veto counts only the upgrade's `APPEND`. To tell the upgrade's apart, check the state LWS is in (`LRS_WAITING_PROXY_REPLY` is in the archive's strings) or that the proxy's reply was seen. Cost if wrong: every user behind a proxy is refused with `Redirect`.
2. **`http_proxy` from the environment.** LWS 3.0 reads `getenv("http_proxy")` when `http_proxy_address` is null: the bundled `context.c.o` imports `getenv`, and the archive holds the string `http_proxy` (`strings`/`nm` on `ThirdParty/libWebSockets/libwebsockets/lib/Unix/x86_64-unknown-linux-gnu/Release/libwebsockets.a`). The engine's `IWebSocket` inherits this too. Recommendation: follow the engine and leave it (one doc line in §2.2), unless the owner wants VaRest to follow only the engine's proxy setting. Then VaRest would have to set an explicit empty proxy, which LWS 3.0 may not accept: measure it. **Owner question.**
3. **Ping payload and RTT.** Recommendation: 8 bytes, a big-endian `uint32` sequence and a `uint32` count of milliseconds since the connection opened, both from the service thread [ping.pong_payload_echo]. A PONG that matches the newest ping still unanswered gives `Pong{Seconds = RTT}`. Any other PONG, unsolicited or stale [ping.unsolicited_pong_delivered], counts as liveness only. The EWMA and `GetLatency*` belong to the socket layer (spec §5). A ping is a control frame: it goes before the next data fragment when `HeldBytes == 0`, never as a second write in one `WRITEABLE`.
4. **Ping defaults at the transport.** Spec §5 turns ping on for every *socket* at 20 s / 10 s, with 0 disabling it. Recommendation: the request defaults to the same 20 s / 10 s, so a direct user of the transport gets the spec's behaviour. W1a's tests last less than 20 s and are unaffected. `PingTimeout` is armed at a ping and cleared by any inbound bytes after it: a `RECEIVE` chunk or a PONG ("no pong **and** no inbound bytes", §2.5). On expiry: kill, then `Closed{1006, By = Heartbeat, Failure = HeartbeatTimeout}`.
5. **Flow control.** Recommendation: pause inside `RECEIVE` when, after a push, `PendingInboundBytes > MaxPendingInboundBytes` (16 MiB): `lws_rx_flow_control(wsi, 0)` [rx.flow_pause_stops_callbacks]. Resume when `Consumed` brings the count down to half or below. `Consumed` runs on the consumer thread, so it posts a resume command once per crossing (an atomic flag), and the command runs `lws_rx_flow_control(wsi, 1)` [rx.flow_resume_from_command, rx.flow_resume_form]. The incomplete assembly is not counted (SW-6 was not adopted). The bound is therefore soft, by at most one message (≤ `MaxMessageBytes`) plus one 64 KiB chunk; §2.3 gets that sentence. The pause is per connection and never drops data.
6. **Deadline suspension (SW-5 e).** Recommendation: while paused, the ping-timeout and idle deadlines are neither armed nor checked, and no ping is sent: nothing could answer it, because LWS is not reading. At resume, both deadlines are re-armed from the resume time and the ping interval restarts. Any end while paused sets `FVaRestSocketEnd::bWhileReadPaused` (a new field; W5 maps it to `FVaRestSocketClose::bWhileReadPaused`).
7. **The idle deadline (SW-5 d, D32).** Recommendation: add `IVaRestSocketConnection::SetIdleDeadline(double Seconds)`. It is game thread, posted as a command, and 0 clears it. The deadline is armed when the command arrives and re-armed by each `RECEIVE` chunk of a data frame; PONGs do not count. On expiry: kill, then `Closed{1006, By = Heartbeat, Failure = IdleTimeout}`, reported at the decision. The interface gains one virtual, the fake records it, and nothing else changes.
8. **Auto-replies (SW-5 a, b).** Recommendation: `struct FVaRestSocketAutoReply { TArray<uint8> Match; TArray<uint8> Reply; }` (plain C++; W5 maps settings onto it). Rules match a whole assembled **text** message, exact bytes, after its UTF-8 check. The message is still delivered, with `FVaRestSocketEvent::bAutoReplied` set (a new field). Replies wait in a lane in `FConn`, each with its 16-byte headroom. A reply is written in `OnWriteable` when `NextFragment == 0` and `HeldBytes == 0`, ahead of the outbox head. Replies are not counted in the buffered amount and are dropped only when the connection ends. A close we queue goes after the replies queued before it. Since nothing is dropped, a Warning fires once a connection has 1024 replies waiting. The probe measured the reply 4.0 ms after the push, with 28 of 32 fragments still queued [tx.autoreply_between_messages, tx.autoreply_delay_ms].
9. **`SO_SNDBUF` (SW-5 c).** Recommendation: in `OnEstablished`, only for a connection with rules: `setsockopt(lws_get_socket_fd(wsi), SOL_SOCKET, SO_SNDBUF, 262144)`. Linux reports double the value [tx.so_sndbuf_ws, tx.so_sndbuf_wss]. The Windows `SOCKET` type and `char*` optval go behind `PLATFORM_WINDOWS`, as a release-pass item (VaRest-b4d). A failure logs a Warning and is not an end. A testing hook reads `getsockopt` back for the test (≥ 262144).
10. **The monolithic run (VaRest-5ia, VaRest-rti's proof).** `VaRestTests` is UncookedOnly and never enters a game target, so the automation suite cannot run in a monolithic game. Recommendation: add a dev-only console command, `VaRest.WebSocket.Smoke <ws url> <wss url>` in `VaRestWebSocket` under `!UE_BUILD_SHIPPING`. It runs a VaRest socket and an engine `IWebSocket` at once, over ws and wss, and logs one result line. Cook `VaRestHost` for Linux, run the monolithic Development game with `-ExecCmds="VaRest.WebSocket.Smoke …; Quit"` against the test server, and read the log for: the startup order (the engine's context, then VaRest's at `StartupModule`), both echoes, the SSL-module `SSL_CTX` [tls.ssl_module_ctx], and D21's one-time warning. **Owner question:** this run (a cook) in W1b, or in W6 with the other packaged runs?
11. **Address selection** (only if W1a Task 7 found that LWS 3.0 tries the first resolved address only): recommendation: leave LWS's choice in W1. Adding `LWS_SERVER_OPTION_DISABLE_IPV6` would break IPv6-only networks (iOS review rules). Resolving in VaRest and connecting by address, with the name as `Host`, keeps the TLS name (the name follows `Host`, [tls.trusted_ca_verified]), but it is a W2 reconnect concern (try the next address). Record it in the bead.

## Task outline (about 8 tasks)

1. **B1 — A CONNECT proxy in the test server, and the probe** (question 1): `Tools/testserver/proxy.py` adds a CONNECT listener. The runner passes its port as `-VaRestTestProxy=<host:port>`. It journals each `CONNECT` line and its headers, with an optional `?deny=403`. Selftests are in `ws_selftest.py`. A probe test, `Probe.VaRest.Lws.Handshake.ProxyAppendCount`, counts `APPEND_HANDSHAKE_HEADER` and certificate checks per attempt through the proxy, ws and wss, and records the LWS state at each. Passport rows are added for both counts. The `http_proxy` environment variable is measured too (question 2).
2. **B2 — The transport through a proxy**: `FServiceOptions::ProxyAddress` (test transports only; the default transport keeps the engine's setting). The redirect veto is fixed if B1 requires it, and W1a's redirect suite must still pass. Integration tests `Proxy.Open` (ws, wss; the proxy's journal shows the CONNECT with the target's host:port and no `Authorization`), `Proxy.Denied` (`ConnectFailed`, the "ERROR proxy: HTTP/1.1 403 Forbidden" row of Task 5's table) and `Proxy.Redirect` (still refused).
3. **B3 — Protocol ping and RTT** (questions 3, 4): request fields, the ping writer in `OnWriteable` (a control frame between fragments), `CLIENT_RECEIVE_PONG` → `Pong`, and the ping-timeout kill. Tests: `Ping.Rtt` (`/ws/echo`), `Ping.SilentServer` (`/ws/silent`, ended `Heartbeat` within `PingInterval + PingTimeout + 0.25 s`), `Ping.DuringLargeSend` (a 16 MiB fragmented send; the journal shows PINGs between fragments, `rx.control_inside_fragmented`'s mirror), `Ping.Unsolicited` (`/ws/serverping?unsolicited=1` keeps the link alive, no RTT) and `Ping.Disabled`. **Restore-the-bug 10:** never arm the deadline, and `Ping.SilentServer` runs to its test deadline.
4. **B4 — Receive flow control** (question 5): pause, resume as a command, the soft bound. Tests: `Flow.SlowConsumer` (`/ws/flood`, `bAcknowledge = false`, `PendingInboundBytes` stays within `Max + MaxMessageBytes + 64 KiB`, the server's journal shows writes blocked [rx.flow_backpressure_reached_server], then all bytes arrive intact after acknowledging) and `Flow.ResumeBelowHalf`. **Restore-the-bug 16:** never pause, and `Flow.SlowConsumer` exceeds `MaxPendingInboundBytes`.
5. **B5 — The idle deadline and suspension** (questions 6, 7): `SetIdleDeadline` (interface, fake, transport), `IdleTimeout`, suspension of both deadlines while paused, `bWhileReadPaused`. Tests: `Idle.Fires` (`/ws/silent`), `Idle.PongsDoNotCount` (`/ws/serverping`), and the SW-5 test: `Flow.SlowConsumerKeepsDeadlines` (paused for longer than both deadlines, the link survives; a drop while paused carries `bWhileReadPaused`).
6. **B6 — Auto-replies, the reply lane, `SO_SNDBUF`** (questions 8, 9): rules, `bAutoReplied`, the lane at the boundary, outside the buffered amount, never dropped, the 1024 Warning, the socket buffer. Tests: `AutoReply.AtBoundary` (`/ws/sink?push=2&after_frames=N` during a 16 MiB fragmented send: the server's messages are A, "3", B, the SW-5 table's test), `AutoReply.NotCounted` (the buffered amount is unchanged by replies), `AutoReply.TextOnly`, `AutoReply.SendBuffer` (`getsockopt` ≥ 262144 with rules, the OS default without). The fake gains `bAutoReplied` scripting.
7. **B7 — The monolithic run** (question 10): the smoke command, the cook and run commands (written out in full, with expected log lines), the startup-order log lines that prove VaRest-rti's policy, VaRest-5ia's checks in a shared copy (`DescribeLwsCopy` reports the executable; the log level is the engine's, D21), and D21's warning when the engine's Verbose setting meets query tokens.

## Lessons to carry (from W0 and W1a)

- One test transport at a time (VaRest-rti).
- `PumpUntil` is not re-entrant: never call a helper that pumps (`FetchJournal`) inside a `PumpUntil` predicate; loop around it instead.
- Every WebSocket integration test calls `ExpectLwsLines` first, because Warnings become errors (`AutomationControllerSettings.cpp:14`).
- Connect TCP by IP (`TcpAddressOverride`, redirect targets by IP), because `localhost` resolves to `::1` first on this host.
- A kill lands up to about 1 s after the decision unless the wait is short: assert the report time, not the fd's end.
- A restore-the-bug must break the path the test sees. LWS's own callbacks also end connections (W1a's `EndForShutdown` lesson), so assert the failure kind and `By`, not only the count of terminal events.
- Wait for the server's journal with `wait_ms`, never with a fixed sleep.
- Compare error strings and protocols with `ESearchCase::CaseSensitive`.
- A header parameter must not take a member function's name (`Count` vs `Wanted`, C4458).
- Never `GetValue()` an unchecked `TOptional`.
- Stage only your files; other agents commit in this tree.

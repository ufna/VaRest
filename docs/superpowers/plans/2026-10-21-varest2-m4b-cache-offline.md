## The seam with M4a

M4a leaves, ready for M4b:

- The chain with room in front of `Retry`: custom Outer → **[M4b: offline queue → cache]** → Retry → AuthGate → boundary → AuthApply → custom PerAttempt → log → limiter → transport (`FClientState::Publish`).
- `FExchangeState::Interrupt` (a stage that holds an exchange waiting), `ClassifyAttempt` (the final outcome's kind; the queue reacts to `Connection` after the retries), `FailureMessage` and the detail-to-kind table (`VaRestClassify.cpp`) for the new details M4b adds.
- The trace payloads and enums: `FVaRestTraceNote` with the cache and queue kinds, `EVaRestTraceMarkerKind::Online/Offline`, `FVaRestTraceStarted::CachePolicy/CacheLookup/QueueReplayOf`, `EVaRestTraceOutcome::Queued`; `FTraceRecorder` for tests; `FHttpStats` (add `CacheLookups`, `CacheHits`, a ratio stat).
- Disk IO pattern: `UE::Tasks` with a counter pair like `DecodeTasksLaunched/HandedBack`, so `FTestRig::Drain()` can wait for cache and queue IO (extend `Drain`).
- The session: a replayed queue item gets auth re-applied by `AuthApply` (spec §4.4 "Auth is re-applied") with no extra code.

## Design questions the M4b plan must settle (with the writer's recommendation)

1. **The cache key's auth identity vs the stage order (a spec contradiction).** Spec §4.3 keys the cache on "SHA-256 of the applied `Authorization` value", but spec §4's chain puts the cache before Retry and Auth, where nothing is applied yet. Recommendation: the cache stage computes the identity itself by running `ApplyCredentials(Auth, scratch target)` on the current session (the value `AuthApply` will apply to the next attempt), hashing every header the auth and the session would set (not only `Authorization`: an API key in `X-Api-Key` or the query is an identity too). Cost if wrong: a cached entry stored under one identity while the attempt used a refreshed token of the same identity (same user, so harmless); a Replaced session changes the key (correct).
2. **Who owns connectivity before the Hub exists (M5).** Recommendation: `FVaRestConnectivity` (VaRestHttp, game thread), one process-wide instance for scope 0, which every client uses by default (`WithConnectivity()` to replace it); M5's `UVaRestHub` makes one per game instance and hands it to its clients. Its events become the Hub's `OnConnectivityChanged`.
3. **Client identity for the queue directory** (spec §4.4: "the API asset path, or the explicit name in `.WithOfflineQueue(Name)`"): M4b has no asset; `WithOfflineQueue(Name)` is required for a code-first client that queues (Config error otherwise). The name is sanitised into a directory name; two clients with one name share one queue (documented).
4. **The queue file format and its atomicity.** One file per item (`<sequence>.json`: verb, resolved URL, non-auth headers, body bytes as base64, idempotency key, tag, created UTC), written to a temp name and renamed (the M3 `MoveIntoPlace` helper), on `UE::Tasks`; an index rebuilt from the directory at start. Session headers and credentials are never persisted (spec: "non-auth headers").
5. **Replay.** FIFO per client, one at a time (spec §4.4), through the normal pipeline minus the offline stage, flag `QueueReplayOf {QueueId, OriginalRequestId}` (IN-1); its outcome reaches only `OnQueuedResult(QueueId, Tag, bSuccess, Response, Error)` (spec). A replay that fails with `Connection` stays queued (connectivity goes offline again). When replay starts: on `Online` and at client creation when the Hub is online.
6. **Builder and client surface** (names that become pins in M5: list them in the plan's freeze decision): `QueueWhenOffline()`, `OnQueued(Func)` (the builder's callback with the queue id), `Cache(FVaRestCachePolicy)`, `NoCache()`; client `WithCache(FVaRestCachePolicy)`, `WithOfflineQueue(FStringView Name)`, `ClearCache()`, `GetQueuedCount()`, `FlushQueue()`, `OnQueuedResult()`; USTRUCT `FVaRestCachePolicy` (`None | Memory | MemoryAndDisk`, 8 MiB / 64 MiB caps, default TTL, `bServeStaleOnError`), UENUM for the cache mode, `FVaRestQueuedResult` if the event's arguments become a struct.
7. **Eligibility** (spec §4.4): idempotent or `.Idempotent()`; streamed or multipart-file bodies are a `Config` error at `Send`; a `SaveTo` request is not queueable either (its file target may not exist at replay) — decide and document.
8. **Cache semantics**: GET/HEAD 200 only; `Cache-Control` `max-age`, `no-store`, `no-cache` (and `private`/`public` ignored for a client cache); `Expires` as a fallback; default TTL; revalidation with `If-None-Match` / `If-Modified-Since`, a 304 refreshing the metadata and serving the cached bytes with `bFromCache` (IN-2 `bConditional`); `bServeStaleOnError` serving stale when offline (IN-4 `CacheServedStale`); bytes cached, decoded per request (spec); LRU eviction in memory and on disk (`Saved/VaRest/Cache`); `ClearCache()` on logout? (spec is silent: recommend `ClearSession` does not clear the cache, the auth identity in the key already separates users).
9. **Connectivity rules** (spec §4.4): offline after a transport connection failure; online after any success or a probe success (`ProbeInterval` 10 s; probe = the head of a queue or an optional `HealthUrl`); mobile hint `FPlatformMisc::GetNetworkConnectionType()` (open the engine header and cite it); `VaRest.Http.ForceOffline 1` (non-Shipping) forces offline for tests and the Inspector's checklist; IN-9 markers on each change. A request that fails with `Connection` while offline and is not queued gets `Kind=Offline`? (spec §3.3: "`Offline` (no connectivity, not queued, or queued item expired)") — decide when a plain request becomes `Offline` instead of `Connection`.
10. **M5 carries to record**: settings for cache and queue directories (spec §5.5), the asset's `bQueueWhenOffline` per endpoint, the Hub's flush on `Deinitialize` (spec §5.2).

## Task outline (about 11 tasks)

1. **B1 — Cache policy, key and `Cache-Control`** (pure): `FVaRestCachePolicy`, the key (verb, URL, `Vary`-relevant request headers, the auth identity of question 1), a `Cache-Control`/`Expires` parser, freshness; unit tests with exact vectors.
2. **B2 — Memory store**: LRU by bytes (8 MiB), game thread, entries with metadata (status, headers, ETag, Last-Modified, stored-at, max-age).
3. **B3 — Disk store**: `Saved/VaRest/Cache`, an index, LRU by bytes (64 MiB), all IO on `UE::Tasks` with a `Drain`-visible counter, atomic writes, corruption tolerated (a bad entry is a miss and is deleted).
4. **B4 — The cache stage**: lookup (fresh hit answers without the network, IN-1 `CacheLookup`), store on 200 (IN-4 `CacheStored`), revalidation with conditional headers and the 304 path (IN-4 `CacheRevalidated`, IN-2 `bConditional`), `bFromCache`, stale on error/offline (`CacheServedStale`), `ClearCache()`, the stats ratio; tests on the fake.
5. **B5 — Connectivity**: `FVaRestConnectivity`, transitions from transport outcomes, the probe timer on `IVaRestClock`, the mobile hint, `ForceOffline` cvar, `OnConnectivityChanged`, IN-9 `Online`/`Offline` markers.
6. **B6 — The queue store**: per-client directory, item files, the limits (`MaxQueued` 256, `MaxAge` 24 h), expiry, IO on `UE::Tasks`.
7. **B7 — The offline stage**: eligibility (`Config` errors), queue on `Connection` after the retries (it sits outside `Retry`) or at once while offline, `OnQueued(QueueId)` instead of success/error, IN-4 `Queued`, IN-5 `Outcome = Queued`.
8. **B8 — Replay**: FIFO, one at a time, auth re-applied, minus the offline stage, `OnQueuedResult`, `QueueReplayOf`, survival across a client re-creation (the "app restart" case: a new client with the same queue name replays what is on disk), IN-4 `QueueExpired` with `Kind=Offline`.
9. **B9 — The IN-17 goldens**: cache hit; 304; offline queued + replay + expiry; attach mid-flight with a queued item.
10. **B10 — Test server and integration**: `/etag` (exists) for revalidation against curl, `Cache-Control: max-age` routes, an offline run (`ForceOffline`, or a client pointed at a closed port) with queue then replay against the server, a restart replay.
11. **B11 — Close M4**: CLAUDE.md freeze line for M4b's types; monolithic Development + Shipping builds; the per-module NoPCHs / `bUseUnity = false` compile (dry-run first with `-WriteOutdatedActions`); the MSVC shadowing sweep; `bd close VaRest-6br` when the milestone exit (spec §8: "stage tests green, restore-the-bug done") holds for M4a and M4b together.

## Lessons to carry (from M3 and M4a)

Every test drains what it sends, with counters (extend `FTestRig::Drain` with the cache and queue IO counters) rather than a fixed wait; no index after a non-fatal check; the virtual clock for TTLs, probes and `MaxAge`; restore-the-bug for each behaviour above; disk IO never on the game thread (spec §1); persisted files never hold credentials or session headers.

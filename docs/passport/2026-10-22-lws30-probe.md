## How the probe works

- One `lws_context` per test with WebSocket spec 2.1's shape: one protocol `varest` (`rx_buffer_size` 64 KiB), `CONTEXT_PORT_NO_LISTEN`, `PEER_CERT_NOT_REQUIRED | DISABLE_OS_CA_CERTS | JUST_USE_RAW_ORIGIN`, 32 KiB header buffers, `ws_ping_pong_interval = 0`.
- One service thread per context, waiting up to 10 s in `lws_service` and woken by `lws_cancel_service`; game-thread commands (connect, write, close, kill, flow control) run inside `LWS_CALLBACK_EVENT_WAIT_CANCELLED` (`svc.commands_*` compares that with the engine's between-calls placement).
- Facts about LWS's own timers (handshake, close-ack and idle timeouts, the blackholes) wait at most 100 ms instead: LWS checks its deadlines only when `lws_service` returns. Each kill latency is measured with both waits (`*_short_wait` rows).
- Library outcomes (a connection that opened, ended or echoed) are facts, never failed tests; a test fails only when the harness did not run. Calls that may end the process (`Probe.VaRest.Risky.*`) run one case per process after a `PENDING` line.
- Every callback is recorded in order with its length, flags and a copy of its bytes; the server side comes from `ws.py`'s journal (`GET /ws/journal`) over HTTP, never through the library under test.
- TLS against the test server's committed throwaway CA (`Tools/testserver/certs/`).
- The probe never calls `lws_set_log_level` or `lws_set_allocator`.
